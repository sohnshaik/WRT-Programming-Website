Git & GitHub

Version control is non-negotiable. A programmer who can't use Git can't contribute to the team codebase during build season.

Before anything else: Make sure you have a GitHub account and you've been added to the WaltonRobotics org. Ask Hrehaan or Sohan to add you if you haven't been.

What is Git?

Git is version control software. It keeps a complete history of every change ever made to a codebase, lets multiple people work on different parts of the code at the same time, and lets you recover from mistakes by rolling back to any previous state.

GitHub is a website that hosts Git repositories online so the whole team can access them.

Repository (repo)
The project folder
Contains all the code, plus Git's entire change history. One repo per robot project.
Commit
A saved snapshot
A commit captures the state of your files at a moment in time, with a message explaining what changed.
Branch
A parallel line of work
Work on a new feature in isolation. When it's done, merge it back. Main branch stays clean.
Pull Request (PR)
A request to merge
You open a PR when your branch is ready. Team members review it before it merges into main.

The Commands You'll Use Every Day

terminal — setup (do this once)
# Clone the repo to your laptop
git clone https://github.com/WaltonRobotics/Watergate.git

# Tell Git who you are (use your real name)
git config --global user.name "Your Name"
git config --global user.email "your@email.com"
terminal — daily workflow
# 1. Before starting any work, pull latest changes from main
git checkout main
git pull

# 2. Create a new branch for your feature
git checkout -b feature/shooter-pid

# 3. Make your changes, then stage them
git add .              # stage everything changed
git add Shooter.java   # or stage one specific file

# 4. Commit with a descriptive message
git commit -m "feat: add PID control to shooter subsystem"

# 5. Push your branch to GitHub
git push origin feature/shooter-pid

# Then open a Pull Request on GitHub and request review

Never push directly to main. Always work on a branch and open a PR. Even if you're the only one working on something. This protects the robot's working code from being broken by in-progress changes.

Branch Naming Convention

On 2974 we follow this pattern. Be consistent — it makes it obvious what's in a branch at a glance.

TypeFormatExample
feature/New functionalityfeature/auto-align
fix/Bug fixfix/shooter-pid-oscillation

docs/Documentation or comments onlydocs/intake-javadocs

Writing Good Commit Messages

A commit message is a note to your future self and your teammates. Write it like you're explaining what changed to someone who wasn't there.

commit messages — bad vs good
# BAD — useless
git commit -m "stuff"
git commit -m "fixed it"
git commit -m "changes"

# GOOD — tells you exactly what happened
git commit -m "feat: add encoder-based speed control to shooter"
git commit -m "fix: prevent motor from running when limit switch is triggered"
git commit -m "refactor: extract motor constants to Constants.java"

Merge Conflicts

A merge conflict happens when two branches changed the same line of the same file differently. Git doesn't know which version to keep, so it asks you to decide.

conflict markers in a file
// Git marks the conflict like this:
<<<<<<< HEAD
    double speed = 0.8; // your version
=======
    double speed = 0.6; // their version
>>>>>>> feature/auto-speed

// You delete the markers and keep the right version:
    double speed = 0.8;

VS Code helps a lot here. It shows merge conflicts visually with "Accept Current", "Accept Incoming", and "Accept Both" buttons. You almost never need to edit the raw markers.
